Order Service

Order Service API Contract

Security model, request/response schema, validation rules, and standard error handling.

1. Overview

Service Scope
The Order Service exposes REST APIs for creating, retrieving, updating, and querying purchase orders. All endpoints use OAuth2 JWT authentication, require tenant scoping, and return structured error payloads with trace identifiers for troubleshooting.

2. Security

Authentication

  • Bearer token in Authorization header
  • JWT validated against OIDC issuer
  • Audience and scope checked for order access

Authorization

  • BUYER, PROCUREMENT_ADMIN, SUPPLIER roles supported
  • Tenant isolation enforced by X-Tenant-ID
  • Request context carries correlation ID

Required Headers

  • Authorization: Bearer <jwt>
  • X-Tenant-ID: tenant identifier
  • X-Request-ID: optional but recommended

7. Validation Rules

Business & Input Validation
  • supplierId must be non-empty and exist in the supplier master.
  • tenantId is required and must match the authenticated tenant context.
  • lineItems must contain at least one item and cannot exceed 50 entries.
  • quantity must be greater than zero and less than or equal to 10,000 per line item.
  • unitPrice must be greater than zero and have no more than 2 decimal places.
  • requestedDeliveryDate must be today or in the future.
  • currency must be a valid ISO 4217 code.
  • notes length must not exceed 500 characters.
  • Status transitions must follow the allowed workflow: DRAFT → VALIDATED → APPROVED → SUBMITTED → CLOSED.
  • PATCH updates are rejected when the current order state is not eligible for modification.

HTTP Error Code Description
400 PO_BAD_REQUEST Malformed request body or invalid JSON.
401 PO_UNAUTHORIZED Missing, expired, or invalid bearer token.
403 PO_FORBIDDEN User does not have permission to access the resource.
404 PO_NOT_FOUND Order ID does not exist or is not visible to the tenant.
409 PO_STATE_CONFLICT Update violates current order state or workflow rules.
422 PO_VALIDATION_FAILED Input failed validation or business rule checks.
429 PO_RATE_LIMITED Too many requests exceeded rate limit.
500 PO_INTERNAL_ERROR Unexpected server-side failure or downstream dependency issue.

9. Security & Reliability Notes

Operational Guidance
  • Always send a valid JWT token and include the tenant header for multi-tenant environments.
  • Use X-Request-ID for tracing requests across API, Kafka, and Oracle SCM calls.
  • Retry only on transient failures with exponential backoff for downstream integration issues.
  • Do not expose internal stack traces in public API responses.
  • Use idempotency keys for create and update operations when downstream retries are expected.
