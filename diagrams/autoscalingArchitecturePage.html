📈 Autoscaling Architecture

Dynamic resource scaling across API Gateway, Services, and KEDA with SCM integration

1. Architecture Overview
The autoscaling architecture implements a multi-layer scaling strategy that responds to different performance metrics across the platform. It combines Horizontal Pod Autoscaler (HPA) for request-based scaling, KEDA for Kafka consumer lag-based scaling, and SCM integration as a rate-limiting absorber before Oracle SCM. This ensures optimal resource utilization while maintaining service reliability.

2. API Gateway & Service Scaling (HPA)
Horizontal Pod Autoscaler (HPA) monitors incoming request volume (Requests Per Second - RPS) and automatically scales the number of service replicas. This layer responds to traffic spikes from the API Gateway and ensures services maintain consistent response times.

HPA Scaling Metrics

Target CPU Utilization 70% - Triggers scale-up when exceeded
Target Memory Utilization 80% - Triggers scale-up when exceeded
Requests Per Second (RPS) 1000 RPS per pod - Dynamic scaling threshold
Scale-up Stabilization 30 seconds - Prevent rapid fluctuations
Scale-down Stabilization 300 seconds - Controlled resource release
Min/Max Replicas 3-15 pods - Maintains availability

How HPA Scaling Works:

  1. Metric Collection: Prometheus scrapes metrics every 15 seconds from service pods, including CPU usage, memory consumption, and request latency.
  2. Decision Point: HPA evaluates if current metrics exceed the target thresholds (70% CPU or 1000 RPS per pod).
  3. Scale-Up Action: When thresholds are exceeded, HPA calculates new desired replica count and triggers pod creation in Kubernetes.
  4. Gradual Scale-Down: When metrics drop below thresholds, HPA gradually reduces replicas over 5 minutes to avoid rapid churn.
  5. Load Balancer Update: Kubernetes service DNS automatically routes traffic to new pods through load balancing.
YAML HPA Configuration Example 
apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata:
  name: order-service-hpa
  namespace: production
spec:
  scaleTargetRef:
    apiVersion: apps/v1
    kind: Deployment
    name: order-service
  minReplicas: 3
  maxReplicas: 15
  metrics:
  - type: Resource
    resource:
      name: cpu
      target:
        type: Utilization
        averageUtilization: 70
  - type: Resource
    resource:
      name: memory
      target:
        type: Utilization
        averageUtilization: 80
  - type: Pods
    pods:
      metric:
        name: http_requests_per_second
      target:
        type: AverageValue
        averageValue: "1000"
  behavior:
    scaleUp:
      stabilizationWindowSeconds: 30
      policies:
      - type: Percent
        value: 100
        periodSeconds: 15
    scaleDown:
      stabilizationWindowSeconds: 300
      policies:
      - type: Percent
        value: 50
        periodSeconds: 60
⚡ Key Point:

HPA responds to immediate traffic changes. When API Gateway receives a traffic spike, it distributes requests across existing pods. When CPU/RPS metrics exceed thresholds, new pods are provisioned within 30-60 seconds.

3. Consumer Lag-based Scaling (KEDA)
KEDA (Kubernetes Event Autoscaling) monitors Kafka consumer lag and automatically scales consumer replicas. This ensures that messages flowing through Kafka topics are processed efficiently, preventing backlog buildup and maintaining system responsiveness.

KEDA Scaling Metrics

Kafka Consumer Lag Target: < 1 minute lag across partitions
Lag Offset Per Partition Monitored per partition for granular scaling
Messages Per Partition Determines scaling factor based on queue depth
Consumer Throughput Messages per second per consumer pod
Min/Max Consumers 2-10 replicas - Cannot exceed partition count
Scale Threshold 1000 messages lag per consumer triggers scale-up

How KEDA Scaling Works with Kafka Partitions:

  1. Partition Assignment: Kafka topic has N partitions. Each consumer can be assigned one or more partitions. Maximum replicas = number of partitions.
  2. Lag Calculation: KEDA reads consumer offset from Kafka broker and compares to latest partition offset. Lag = (latest offset - consumer offset).
  3. Aggregate Lag: Sum lag across all partitions assigned to consumer group. KEDA divides by desired messages-per-pod to calculate needed replicas.
  4. Dynamic Scaling: If lag exceeds threshold, KEDA provisions new consumer pods. Kafka automatically rebalances partitions among consumers.
  5. Partition Rebalancing: When new pods join, Kafka stops consumers momentarily, rebalances partitions, then resumes processing from stored offsets.

Kafka Partition Scaling Example

Scenario Consumer Lag Action Result
Normal Load 0-5k messages Maintain 2 consumers Each processes 1 partition, lag < 30s
Moderate Spike 5k-15k messages Scale to 4 consumers Better parallelism, lag reduces to < 1min
High Spike > 20k messages Scale to max (8 consumers) All partitions actively processed, lag cleared
Post-Spike 0-2k messages Scale down after 5 minutes Return to 2 consumers, save resources
YAML KEDA ScaledObject for Kafka Consumer 
apiVersion: keda.sh/v1alpha1
kind: ScaledObject
metadata:
  name: kafka-consumer-scaler
  namespace: production
spec:
  scaleTargetRef:
    name: kafka-consumer
    kind: Deployment
  minReplicaCount: 2
  maxReplicaCount: 10
  pollingInterval: 30
  triggers:
  - type: kafka
    metadata:
      bootstrapServers: kafka-broker-0:9092,kafka-broker-1:9092,kafka-broker-2:9092
      consumerGroup: order-processing-group
      topic: order-events
      lagThreshold: "1000"
      offsetResetPolicy: "latest"
      scaleDownEnabled: "true"
      # Scale metric: desired pods = ceil(totalLag / lagThreshold)
      # If total lag across partitions is 10k and lagThreshold is 1000,
      # KEDA scales to 10 pods (but respects maxReplicas limit)
    authModes: "sasl_plaintext"
  advanced:
    horizontalPodAutoscalerConfig:
      behavior:
        scaleDown:
          stabilizationWindowSeconds: 300
          policies:
          - type: Percent
            value: 50
            periodSeconds: 60
⚡ Key Point:

KEDA scales based on Kafka lag, not just processing speed. If consumers cannot keep up with the rate of messages, consumer lag increases, triggering KEDA to add more replicas. Kafka automatically rebalances partitions among consumers to ensure even load distribution.

4. SCM Integration as Rate Limiter & Request Absorber
The SCM integration layer acts as a critical buffer between T-Mobile's internal services and Oracle SCM Cloud. It implements rate limiting, request queuing, and intelligent retry logic to protect Oracle SCM from being overwhelmed while ensuring reliable order fulfillment.

SCM Integration Specifications

Max Request Rate 1000 requests/second to Oracle SCM
Queue Depth 10,000 pending requests - In-memory buffer
Request Timeout 30 seconds per request
Retry Strategy Exponential backoff (1s, 2s, 4s, 8s, 16s)
Circuit Breaker 50% failure rate triggers open state
Health Check Interval 10 seconds - Detects SCM availability

How SCM Integration Works as a Rate Limiter:

  1. Request Arrival: Order microservices send requests to SCM integration. If rate ≤ 1000 req/sec, request immediately forwarded to Oracle SCM.
  2. Queue Management: If rate exceeds 1000 req/sec, requests are queued locally (max 10k). This prevents overwhelming Oracle SCM.
  3. Token Bucket Algorithm: SCM integration uses token bucket rate limiter. Tokens are generated at 1000/sec rate. Each request consumes 1 token.
  4. Graceful Degradation: When queue reaches 80% capacity, SCM integration returns a 429 (Too Many Requests) status to clients, signaling to back off.
  5. Retry Logic: Failed requests use exponential backoff. Transient failures (timeout, connection reset) are retried automatically.
  6. Circuit Breaking: If Oracle SCM becomes unavailable (>50% failure rate for 1 minute), circuit breaker opens and requests immediately fail fast instead of timing out.

SCM Integration Request Flow

Pseudo-code SCM Integration Rate Limiter Implementation 
public class SCMRateLimiter {
    private static final int MAX_RPS = 1000;
    private static final int QUEUE_CAPACITY = 10000;
    private static final int QUEUE_WARNING_THRESHOLD = 8000;
    
    private TokenBucket tokenBucket;
    private Queue<Request> requestQueue;
    private CircuitBreaker circuitBreaker;
    
    public Response handleRequest(Request req) {
        // Check circuit breaker
        if (circuitBreaker.isOpen()) {
            return new Response(503, "Service Unavailable - SCM unreachable");
        }
        
        // Check queue capacity
        if (requestQueue.size() >= QUEUE_WARNING_THRESHOLD) {
            return new Response(429, "Too Many Requests - Please retry later");
        }
        
        // Try rate limit
        if (tokenBucket.tryConsume(1)) {
            // Sufficient tokens - forward immediately
            return forwardToSCM(req);
        } else {
            // No tokens - queue the request
            if (requestQueue.size() < QUEUE_CAPACITY) {
                requestQueue.add(req);
                return new Response(202, "Request queued for processing");
            } else {
                return new Response(429, "Request queue full");
            }
        }
    }
    
    // Background thread processes queued requests
    private void processQueuedRequests() {
        while (true) {
            if (tokenBucket.waitForTokens(1)) {
                Request req = requestQueue.poll();
                if (req != null) {
                    retryWithBackoff(req, 0);
                }
            }
        }
    }
    
    private void retryWithBackoff(Request req, int retryCount) {
        try {
            Response response = forwardToSCM(req);
            circuitBreaker.recordSuccess();
        } catch (Exception e) {
            circuitBreaker.recordFailure();
            if (retryCount < 5) {
                long backoffMs = (long) Math.pow(2, retryCount) * 1000;
                Thread.sleep(backoffMs);
                retryWithBackoff(req, retryCount + 1);
            } else {
                log.error("Request failed after 5 retries: " + req);
            }
        }
    }
}
⚡ Key Point:

SCM integration protects Oracle SCM by enforcing a strict 1000 req/sec rate limit. Requests exceeding this rate are queued locally and processed gradually. If the queue fills up or Oracle SCM becomes unavailable, clients receive immediate 429 backpressure signals to reduce load, preventing cascading failures.

5. Complete Autoscaling Flow
All three autoscaling mechanisms work together to create a resilient, self-healing architecture that responds to different types of load variations.

End-to-End Request Journey with Autoscaling

  1. Traffic Spike Arrives at API Gateway: RPS increases from 3000 to 8000 requests/second.
  2. HPA Detects High Load: Order service CPU utilization jumps to 85%. HPA triggers scale-up from 3 to 6 pods within 30-60 seconds.
  3. Requests Flow to SCM Integration: Order services send requests to SCM integration layer. Rate limiter passes through 1000 req/sec to Oracle SCM.
  4. Kafka Event Publishing: Accepted requests publish order events to Kafka topic. Multiple partitions distribute events evenly.
  5. Kafka Lag Increases: Consumer lag grows to 15,000 messages as event rate exceeds consumer processing speed.
  6. KEDA Detects Lag: KEDA monitors lag and scales order-processing consumers from 2 to 6 replicas. Kafka rebalances partitions.
  7. Processing Catches Up: With more consumer replicas processing events in parallel, lag gradually reduces back to < 1 minute.
  8. Gradual Scale-Down: After traffic stabilizes, HPA and KEDA gradually reduce replicas over 5-10 minutes, returning to baseline resource usage.

6. Challenges & Solutions in Autoscaling
While autoscaling provides significant benefits, it introduces operational challenges that must be understood and mitigated. This section covers common pitfalls, memory management issues, and scaling oscillation problems along with proven solutions.

⚠️ Challenge 1: Memory Leaks Break Horizontal Scaling

Problem:

Memory leaks prevent horizontal scaling from being effective. If individual pods leak memory over time, scaling up only multiplies the problem. A service that leaks 50 MB/hour means:

  • 3 pods × 50 MB/hour = 150 MB/hour total leak
  • 10 pods × 50 MB/hour = 500 MB/hour total leak
  • Eventually all pods hit OOMKilled (Out of Memory Killed), cascading failure

✓ Solution: Verify Memory High Usage & Implement Memory Limits

  1. Set Memory Limits: Define explicit memory requests and limits in Kubernetes Pod specs to trigger pod restart before OOMKilled state
  2. Enable Liveness Probes: Configure kubelet to restart pods when memory crosses 85% threshold without killing entire pod
  3. Monitor Memory Growth: Track memory consumption per pod over time using Prometheus metrics (container_memory_usage_bytes)
  4. Detect Leaks Early: Alert when memory grows > 10 MB/min or doesn't stabilize after garbage collection
  5. Implement Memory-based HPA: Scale when ANY pod exceeds memory limit (not just average), preventing cascade failures
  6. Regular Pod Recycling: Implement periodic pod rolling restart (e.g., every 24 hours) to clear accumulated memory leaks

⚡ Challenge 2: Scaling Oscillation (Thrashing)

Problem:

Scaling oscillation occurs when the system continuously scales up and down, wasting resources and creating instability:

  • Time 0s: Load drops, HPA scales down from 10 to 5 pods (saves resources)
  • Time 30s: Remaining 5 pods become overloaded, CPU jumps to 90%
  • Time 60s: HPA scales back up to 10 pods (wasteful cycle repeats)
  • Cost Impact: Continuous pod creation/termination, application startup overhead, network churn

✓ Solution: Implement Stabilization Windows & Threshold Buffers

  1. Scale-Down Stabilization: Set stabilizationWindowSeconds to 300-600 (5-10 min) for scale-down operations. Do NOT scale down immediately when metrics drop below threshold
  2. Scale-Up Stabilization: Keep scale-up stabilization short (30-60 sec) to respond quickly to load spikes, but use longer window for scale-down
  3. Threshold Buffers: Create gap between scale-up and scale-down thresholds (e.g., scale-up at 75% CPU, scale-down at 40% CPU), preventing oscillation
  4. Multiple Scaling Policies: Use percentage-based scaling (e.g., increase by 100%, decrease by 50%) instead of fixed replica counts
  5. Target Utilization Tuning: Set target metrics conservatively (60-70% CPU instead of 90%) to provide headroom for sudden load spikes
  6. Minimum Uptime Between Scale Events: Enforce minimum time (e.g., 2 minutes) between consecutive scaling operations

🔄 Challenge 3: Cascading Failures During Rapid Scaling

Problem:

Rapid scale-up can overload dependencies (databases, caches, rate-limited services), causing cascade failures:

  • HPA scales 3 pods → 15 pods instantly (12 new pods starting up)
  • All 15 pods try to establish database connections simultaneously
  • Connection pool exhausted, pods fail, HPA tries to scale up more
  • Entire system collapses from dependency overload

✓ Solution: Implement Gradual Rollout & Dependency Health Checks

  1. Maximum Scale-Up Rate: Configure HPA to scale by fixed percentage per period (e.g., 100% every 15 seconds, max 3 replicas per scale event)
  2. Startup Probe Delays: Kubernetes startupProbe waits for app to fully initialize before marking pod ready, preventing premature traffic routing
  3. Readiness Probe Verification: Health check includes dependency connectivity (database, Redis cache). Pod only becomes "ready" if all dependencies healthy
  4. Connection Pool Scaling: Database connection pool size must scale proportionally with pod count (max connections = pool_size_per_pod × current_replicas)
  5. Rate Limit Awareness: Pods monitor SCM integration queue depth. If queue > 50%, new pods reduce their request rate to avoid overwhelming rate limiter
  6. Bulkhead Pattern: Isolate thread pools for different services. If order-service is scaling aggressively, payment-service can continue normally
YAML Memory-Safe HPA with Oscillation Prevention 
apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata:
  name: memory-safe-hpa
  namespace: production
spec:
  scaleTargetRef:
    apiVersion: apps/v1
    kind: Deployment
    name: order-service
  minReplicas: 3
  maxReplicas: 15
  
  # Configure metrics for robust scaling decisions
  metrics:
  - type: Resource
    resource:
      name: memory
      target:
        type: Utilization
        averageUtilization: 70  # Scale-up at 70% memory
  - type: Resource
    resource:
      name: cpu
      target:
        type: Utilization
        averageUtilization: 75   # Scale-up at 75% CPU
  
  # CRITICAL: Prevent scaling oscillation with stabilization windows
  behavior:
    scaleDown:
      stabilizationWindowSeconds: 600  # Wait 10 minutes before scaling down
      policies:
      - type: Percent
        value: 50            # Scale down by max 50% per period
        periodSeconds: 60    # Evaluate every 60 seconds
      - type: Pods
        value: 2             # Remove max 2 pods per period
        periodSeconds: 60
      selectPolicy: Min      # Choose policy that scales down least
    
    scaleUp:
      stabilizationWindowSeconds: 30   # Respond quickly to load spikes
      policies:
      - type: Percent
        value: 100           # Can double replicas
        periodSeconds: 30
      - type: Pods
        value: 4             # But max 4 pods added per period
        periodSeconds: 30
      selectPolicy: Max      # Choose policy that scales up most

---
apiVersion: v1
kind: Pod
metadata:
  name: memory-aware-pod
spec:
  containers:
  - name: order-service
    image: order-service:v1.0
    
    # Set memory requests and limits to prevent OOMKilled cascades
    resources:
      requests:
        memory: "256Mi"      # Pod needs at least 256MB
        cpu: "250m"
      limits:
        memory: "512Mi"      # Hard limit - pod killed if exceeded
        cpu: "1000m"
    
    # Detect memory leaks early with liveness probe
    livenessProbe:
      exec:
        command:
        - /bin/sh
        - -c
        - |
          # Check if memory usage exceeds 85% of limit (436 MB)
          MEMORY_LIMIT=512
          CURRENT_MEMORY=$(cat /sys/fs/cgroup/memory/memory.usage_in_bytes | awk '{print int($1/1024/1024)}')
          if [ $CURRENT_MEMORY -gt $((MEMORY_LIMIT * 85 / 100)) ]; then
            echo "Memory usage ${CURRENT_MEMORY}MB exceeds 85% of limit ${MEMORY_LIMIT}MB"
            exit 1
          fi
      initialDelaySeconds: 30
      periodSeconds: 10
      failureThreshold: 3    # Restart pod after 3 consecutive failures
    
    # Gradual startup to prevent cascading failures
    startupProbe:
      httpGet:
        path: /health/startup
        port: 8080
      initialDelaySeconds: 0
      periodSeconds: 5
      failureThreshold: 30   # Give 150 seconds for app to start
    
    # Readiness includes dependency checks
    readinessProbe:
      httpGet:
        path: /health/ready    # Must check DB, Redis, SCM Integration
        port: 8080
      initialDelaySeconds: 10
      periodSeconds: 5
      failureThreshold: 3     # Remove from LB after 3 failures

    • 💡 Key Principle:

    7. Key Takeaways

    🎯 Layer 1: Immediate Response

    HPA scales API-facing services based on CPU and RPS metrics. Responds to traffic spikes within 30-60 seconds. Maintains minimum 3 replicas for availability.

    ⚙️ Layer 2: Event Processing

    KEDA scales Kafka consumers based on partition lag. Ensures events are processed within 1 minute target. Scales based on actual processing backlog, not just throughput.

    🛡️ Layer 3: External Protection

    SCM integration enforces 1000 req/sec rate limit to Oracle SCM. Queues excess requests locally with exponential backoff. Circuit breaker protects against cascading failures.

    💡 Design Principle:

    This three-layer autoscaling strategy allows the system to gracefully handle load spikes at any point: immediate scaling for traffic bursts (HPA), intelligent queue management for asynchronous processing (KEDA), and controlled rate limiting for external dependencies (SCM Integration). Together, they ensure reliability while optimizing resource utilization.
